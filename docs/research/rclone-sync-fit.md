# rclone Drive/bisync fit for Syncjetty

Research date: 2026-11-24. Primary-source review only; no implementation, benchmarks, or runtime validation. Latest stable release observed: [v1.76.0, 2026-11-06](https://github.com/rclone/rclone/releases/tag/v1.76.0). Labels below distinguish documented behavior, source observations, and implications requiring validation.

## Decision-relevant summary

- **Drive transport and TUI-controlled setup are documented capabilities.** rclone exposes directory listing, per-file operations, configuration questions, browser OAuth, jobs, and bisync over RC. This does not require users to edit a config file. [RC API](https://rclone.org/rc/), [noninteractive configuration](https://rclone.org/commands/rclone_config_create/).
- **Unmodified bisync does not satisfy the required conflict contract.** `--conflict-resolve none` means rename both versions and copy them to both sides, **not leave both untouched**. Delete-versus-edit instead automatically restores the edited version to the deleted side. There is no documented per-file hold/resume/resolve queue that preserves pending conflicts while other paths sync. [Conflict flags](https://rclone.org/bisync/#conflict-resolve), [v1.76.0 delta implementation](https://github.com/rclone/rclone/blob/v1.76.0/cmd/bisync/deltas.go#L380-L470).
- **Bisync is snapshot/listing based, not a documented persistent Drive changes-cursor engine.** Repeated enumeration can remain a cost even when nothing transfers. A separate application-owned reconciler using rclone as transport is a different option from adopting bisync; neither option is selected here. [Listing collection](https://rclone.org/bisync/#how-check-access-handles-filters), [no-change run example](https://rclone.org/bisync/#reading-bisync-logs).

## Enumeration, change tracking, and repeated scan latency

**Documented:** Each bisync run gathers listings for both roots and compares them to prior history. Its default comparison is size and modification time; checksums can be added. Final `--check-sync` loads and compares the local listing snapshots, not fresh remote contents. Thus history avoids transferring unchanged files, but does not mean remote enumeration is incremental. [Listing collection](https://rclone.org/bisync/#how-check-access-handles-filters), [comparison](https://rclone.org/bisync/#compare), [check-sync](https://rclone.org/bisync/#check-sync).

**Source-observed distinction:** The Drive backend does implement `ChangeNotify`, using `changes.getStartPageToken` followed by polled `changes.list`. The token is a variable inside that running notification goroutine; it starts from a newly obtained token. This is not evidence that bisync consumes or durably checkpoints Drive's change feed, nor is it a documented RC incremental inventory API. Do not equate mount/cache notifications with cross-restart reconciliation history. [v1.76.0 Drive source](https://github.com/rclone/rclone/blob/v1.76.0/backend/drive/drive.go#L3246-L3335).

Mechanisms that can explain slow repeated runs, without claiming measured performance:

- **Tree shape, pagination, and latency:** ordinary listing queries directories; Drive `ListR` batches up to 50 parent IDs and uses `--checkers` for parallel requests. Listing chunks default to 1,000 entries. Deep/wide trees and multiple pages still require requests. [Drive fast-list](https://rclone.org/drive/#fast-list), [list-chunk](https://rclone.org/drive/#drive-list-chunk).
- **Fast-list is not universally faster:** bisync enables it by default. A Drive listing correctness workaround retries empty multi-parent results as individual directory listings; many empty directories can therefore multiply API calls. Bisync documents `--disable ListR` as the way to avoid its default fast-list. Do not simply disable the correctness workaround for speed. [Bisync default](https://rclone.org/bisync/#fast-list-used-by-default), [Drive workaround](https://rclone.org/drive/#drive-fast-list-bug-fix).
- **Pacing, throttling, and retries:** Drive has API rate limits; rclone's minimum API-call sleep defaults to 100 ms with a burst allowance of 100. Shared client quotas and throttling can add delay; changing concurrency/pacer settings is not a guarantee of improvement. Published quota/throughput anecdotes in rclone docs are not Syncjetty measurements. [Pacer settings](https://rclone.org/drive/#drive-pacer-min-sleep), [Drive limitations](https://rclone.org/drive/#limitations), [client ID guidance](https://rclone.org/drive/#making-your-own-client-id).
- **Local work also matters:** reading/comparing saved listings and final listing validation scale with file count; checksum-based comparison can require local file reads. `--download-hash` can download content when hashes are unavailable. Disabling safety checks to reduce latency changes guarantees, not merely performance. [check-sync](https://rclone.org/bisync/#check-sync), [comparison](https://rclone.org/bisync/#compare), [download-hash](https://rclone.org/bisync/#download-hash).

**Open measurement question:** Time listing, local hashing/history processing, throttling/retries, and transfer separately on representative trees (including many empty directories and Shared Drives), comparing default ListR with `--disable ListR`. No performance result was measured in this research.

## Conflict holding and explicit resolution

| Case | Actual bisync behavior | Fit for required untouched pending state |
| --- | --- | --- |
| Both sides new/modified and unequal | Default `none` renames both and propagates both; other policies select a winner and rename/delete the loser. | **No.** Even default preservation mutates names and copies data before user choice. |
| Deleted on one side, modified on the other | Source queues a copy of the edited version back to the deleted side in either direction. | **No.** Edit wins automatically; it is not treated as a held conflict. |
| Identical contents changed on both sides | Equality checks can avoid conflict renaming. | Useful optimization, not a conflict hold mechanism. |

Sources: [documented conflict definition/actions](https://rclone.org/bisync/#conflict-resolve), [loser behavior](https://rclone.org/bisync/#conflict-loser), [v1.76.0 application of deltas](https://github.com/rclone/rclone/blob/v1.76.0/cmd/bisync/deltas.go#L380-L470).

**Filtering is not a proven safe hold workaround.** Changing `--filters-file` requires `--resync`: exclusions otherwise make previously listed files appear deleted. Resync is a merge/copy operation with different semantics, not a pending-conflict baseline update. Other include/exclude flags being accepted does not establish safe dynamic conflict exclusion and later reintegration. No documented supported way was found to preserve per-file pending history while advancing unrelated files. [Filter safety](https://rclone.org/bisync/#filters-file), [resync](https://rclone.org/bisync/#resync).

**Implication:** Meeting keep-local/keep-Drive/keep-both with untouched pending files needs additional reconciliation/state ownership or upstream changes, not merely a conflict flag. RC provides `operations/copyfile`, `operations/movefile`, and `operations/deletefile` as action primitives, but not an atomic multi-action resolution transaction or a documented way to inject an approved per-file plan into bisync history. Revalidation after further edits, delete-versus-edit semantics, name collisions for keep-both, interruption recovery, and baseline advancement remain application-level proof obligations. [Per-file RC operations](https://rclone.org/rc/#operations-copyfile), [movefile](https://rclone.org/rc/#operations-movefile), [deletefile](https://rclone.org/rc/#operations-deletefile), [bisync RC parameters](https://rclone.org/rc/#sync-bisync).

## First preview and approval correctness

**Documented:** `--dry-run` suppresses file mutations, and bisync recommends previewing the initial `--resync`. However, the manual explicitly documents a dry-run artifact: because simulated copies do not occur, later phases can report deletions that a real run would not perform. Raw dry-run logs therefore are not automatically a correct user-facing action list. [Getting started](https://rclone.org/bisync/#getting-started), [dry-run oddity](https://rclone.org/bisync/#dry-run-oddity).

Initial resync defaults to Path1 winning same-name differences, always copies one-sided files, and ignores normal conflict-resolution flags; it cannot represent an unresolved same-name conflict without choosing/overwriting something. A later real run re-examines live state: neither CLI nor documented `sync/bisync` RC parameters accept a frozen approved plan or per-item preconditions. **[INFERENCE]** Approval must be bound to validated inputs, with a changed preview requiring renewed approval; a dry-run followed later by an ordinary resync alone does not establish that guarantee. [Resync modes](https://rclone.org/bisync/#resync-mode), [RC contract](https://rclone.org/rc/#sync-bisync).

## TUI OAuth, configuration, and background control

- **Documented setup protocol:** `config/create` / `config/update` support `nonInteractive`, `continue`, `state`, and `result`. The CLI version documents JSON questions and completion when `State` becomes empty. `config/providers` supplies option metadata. A TUI can render these steps, rather than expose rclone's terminal questionnaire or manual config editing. [Configuration protocol](https://rclone.org/commands/rclone_config_create/), [RC create](https://rclone.org/rc/#config-create), [RC update](https://rclone.org/rc/#config-update).
- **Browser authorization:** Drive uses a temporary loopback callback server, normally `127.0.0.1:53682`. RC exposes `config/oauthstatus` with an authorization URL and `config/oauthstop` to cancel an interrupted flow. Completion/cancellation and concurrent account setup should be exercised against the pinned version; the docs do not promise independent simultaneous OAuth sessions. [Drive OAuth](https://rclone.org/drive/#configuration), [OAuth status](https://rclone.org/rc/#config-oauthstatus), [OAuth stop](https://rclone.org/rc/#config-oauthstop).
- **Folder selection and execution:** `operations/list` returns structured listings for a folder picker; Drive can be rooted by `root_folder_id`. `sync/bisync` has an explicit RC endpoint; `_async` plus job status enables nonblocking control. An independently managed `rcd` process can outlive the TUI, but installing/supervising that background process is Syncjetty's responsibility, not an automatic consequence of using RC. [List API](https://rclone.org/rc/#operations-list), [Drive root](https://rclone.org/drive/#root-folder-id), [async jobs](https://rclone.org/rc/#running-asynchronous-jobs-with-async-true), [rcd](https://rclone.org/commands/rclone_rcd/).
- **Important current onboarding caveat:** rclone says its shared Drive OAuth client ID is being retired and will stop working during 2026; relying on it is unsuitable for a new release. Product-owned OAuth client provisioning and Google's applicable consent/verification requirements remain necessary; rclone does not remove them. Full existing-folder sync also cannot use rclone's `drive.file` behavior as a drop-in replacement for full Drive access. [Client ID retirement](https://rclone.org/drive/#making-your-own-client-id), [scopes](https://rclone.org/drive/#scopes).

## Safety caveats affecting an engine decision

- Bisync calls itself advanced and warns of data loss. Preserve its working history; never automatically run resync after every error. Resync can resurrect deletions and overwrite a newer Path2 version under its default Path1 preference. `--check-access`, default 50% `--max-delete`, locking, `--resilient`, and `--recover` have different purposes; they are not a substitute for pending-conflict semantics. Completely empty normal-run roots are rejected as a safety check, which also needs deliberate handling for legitimate delete-all. [Manual](https://rclone.org/bisync/), [resync](https://rclone.org/bisync/#resync), [recovery](https://rclone.org/bisync/#recover).
- Concurrent modifications still carry documented risk despite the snapshot model; overlapping bisync jobs require caution. `--check-sync` checks history snapshots, not actual remote equality. [Concurrency](https://rclone.org/bisync/#concurrent-modifications), [locking](https://rclone.org/bisync/#lock-file), [check-sync](https://rclone.org/bisync/#check-sync).
- Drive duplicate names and delayed Shared Drive fast-list visibility can affect correctness. Google Docs exports/imports are not ordinary lossless files: local renames can delete/recreate the native document, imports can be lossy, and native docs lack size/checksum information needed by some comparison modes. These require an explicit product policy, not silent assumptions. [Drive duplicates/visibility](https://rclone.org/drive/#duplicated-files), [recopy caveat](https://rclone.org/drive/#rclone-appears-to-be-re-copying-files-it-shouldn-t), [bisync Google Docs](https://rclone.org/bisync/#google-docs-and-other-files-of-unknown-size).
- RC access is equivalent to shell access, including local file access and stored credentials; it has no per-endpoint capability system. Use protected local IPC/authentication and do not expose it as a harmless progress API. [RC security](https://rclone.org/rc/#security).
- Version pinning matters: v1.76.0 includes fixes for bisync conflict listings, conflict comparisons, skipped-file loops, RC dry-run/max-delete handling, conflict rename collisions, and a Drive fast-list hang. Older installed rclone must not be assumed equivalent to current documentation. [v1.76.0 changelog](https://rclone.org/changelog/#v1-76-0-2026-11-06).
