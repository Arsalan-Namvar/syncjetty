# Native Google Drive API: first-release fit

Research date: 2026-11-24. Scope: Linux desktop/TUI, two-way folder sync, background operation, approval before first reconciliation, and explicit resolution of conflicts (including delete-vs-edit). Research only: no engine selection, implementation, provisioning, or performance measurements. **[INFERENCE]** marks Syncjetty implications rather than Google guarantees.

## Initial inventory versus incremental changes

- `changes.getStartPageToken` starts **future** change tracking; it is not an inventory of existing files. Initial discovery needs `files.list`, following every `nextPageToken`. List pages contain at most 1,000 files; pagination tokens are typically valid for hours, may be rejected, and additions/removals can affect results. An `incompleteSearch=true` result is not a complete inventory; narrow the corpus instead of treating missing files as deletions. Sources: [Changes resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/changes), [files.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list).
- **[INFERENCE]** Capture a changes token **before** initial enumeration, build the inventory, then replay changes from that token to catch concurrent activity. This is not an atomic snapshot. Persist the inventory/baseline and pending work durably; reconciliation must tolerate repeated observations. The first preview needs revalidation if either side changes before approval. No remote writes should occur just to construct that preview.
- Incrementally, drain `changes.list` using `nextPageToken`, then save the terminal `newStartPageToken` for the next poll. Both change-page token types are documented as non-expiring; pages contain at most 1,000 changes. Changes expose current item state, **not content deltas or a complete event history**: a newer entry can replace an older entry for the same item. Determining what changed requires comparison with persisted prior state. Sources: [changes.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/changes/list), [tracking changes](https://developers.google.com/workspace/drive/api/guides/about-changes).
- `changes.list` has user/shared-drive scoping and My Drive restriction options, but no arbitrary subtree `q` filter. **[INFERENCE]** A selected-folder sync needs an ID/parent index to filter changes, detect moves across its boundary, and discover descendants when an existing folder enters the selected tree. If shared drives are offered, track their separate logs: a member's user log alone misses changes, and joining a shared drive produces a drive event rather than an inventory of its children. Sources: [changes.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/changes/list), [shared-drive tracking](https://developers.google.com/workspace/drive/api/guides/about-changes#track_shared_drives).

## Notifications, polling, and limits

- Drive push is an **HTTPS webhook**, not a connection pushed directly to the TUI. Notifications have empty bodies and supply neither file contents nor metadata/paths; the receiver still calls Drive to obtain changes. Channel lifetimes are at most one week for `changes` and one day for `files` (default: one hour), with replacement rather than automatic renewal. **[INFERENCE]** A standalone desktop daemon can poll the durable changes cursor without requiring a public webhook service; polling interval trades detection latency against requests. Push would add reachable receiver infrastructure and renewal management, and reconnect/startup still needs cursor catch-up rather than assuming notifications constitute a replayable queue. Source: [push notifications](https://developers.google.com/workspace/drive/api/guides/push).
- **Quota changed in 2026:** Google's current limits page says projects created on/after May 1, 2026 use **1,000,000 quota units/minute/project** and **325,000 units/minute/user/project**; projects used during November 2025–April 2026 retain prior quotas. Costs include 100 units for `files.list`/`changes.list`/watch, 5 for metadata `files.get`/start token, 50 for edits, and 200 for media download/export. These are **units, not request counts**. Project quotas are shared across installations using that project. Source: [usage limits and per-method costs](https://developers.google.com/workspace/drive/api/guides/limits).
- The same page lists a **1 TB/day/project egress threshold** and **400,000,000 units/day/project billing threshold**, while saying billing details will be announced later in 2026 with notice. It also retains a statement that requests per day are unlimited within minute quotas. **[INFERENCE]** Do not promise unlimited free traffic or hard-code historical 12,000-requests/minute assumptions; verify the actual project's quotas and current billing terms before release. No billing setup was performed. Source: [usage limits](https://developers.google.com/workspace/drive/api/guides/limits).
- Backend throttling can produce 403/429 even apart from the published quota; Google recommends randomized truncated exponential backoff. Workspace users additionally face 750 GB/day upload/copy limits and a 5 TB maximum uploaded file. Delivered notifications do not consume quota; watch/stop calls do. Source: [usage limits](https://developers.google.com/workspace/drive/api/guides/limits).

## OAuth: publisher work versus user friction

- The publisher must enable Drive in a Cloud project, configure consent/scopes, and create a **Desktop app** OAuth client. Desktop clients are public: an embedded client secret cannot be treated as confidential. Google's flow uses the system browser, PKCE, and a local loopback HTTP redirect on an available port. Out-of-band copy/paste authorization is no longer supported; embedded authorization user agents are disallowed. **[INFERENCE]** TUI-led browser sign-in and folder selection can avoid user config editing; requiring each user to create a Cloud project would shift publisher setup onto users, not remove it. Source: [desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app).
- `drive.file` is non-sensitive **per-file** access for files created/opened/shared with the app; do not assume choosing a folder grants recursive access to all pre-existing/future children. `drive` grants full management and is restricted; backup/sync apps are an explicitly qualifying category, but public distribution still needs restricted-scope verification. Google says storing/transmitting restricted data on servers triggers security assessment requirements. **[INFERENCE]** Broad existing-folder sync makes scope/verification a release dependency; a local folder-selection UI does not turn a broad OAuth grant into folder-scoped authorization. Source: [Drive authorization and scope qualifications](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).
- Desktop authorization returns refresh tokens for unattended access. Store tokens securely across invocations; losing them requires consent again. External apps left in **Testing** issue refresh tokens expiring after seven days for Drive scopes. Tokens can also stop working through revocation, six months of nonuse, token-count limits, time-limited grants, or admin policy. There is a 100-refresh-token limit per account/client, after which the oldest is invalidated. **[INFERENCE]** Background sync can outlive the TUI, but must visibly pause and offer in-TUI reconnection when authorization fails; it cannot guarantee permanent unattended access. Sources: [desktop token handling](https://developers.google.com/identity/protocols/oauth2/native-app), [refresh-token expiration](https://developers.google.com/identity/protocols/oauth2#expiration).

## Filesystem mismatches and deletion safety

| Drive behavior | First-release implication [INFERENCE] |
|---|---|
| File IDs are stable for the file's lifetime, even through renames. Names are not necessarily unique **within one folder**. Parent IDs identify placement. [File characteristics](https://developers.google.com/workspace/drive/api/guides/about-files#file_characteristics), [File resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files) | Track remote identity by ID, not path/name. Persist local identity correspondence for rename/move detection. Duplicate sibling names cannot both occupy the same Linux path: a visible, stable disambiguation/hold policy is required; never overwrite one silently. |
| Ordinary blobs download through `files.get?alt=media`; downloads may be restricted. Blob MD5 and available SHA checksums do not cover Google Docs Editors files. `version` changes for metadata as well as content. [Downloads](https://developers.google.com/workspace/drive/api/guides/manage-downloads), [File resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files) | Binary-file reconciliation can compare provider checksums and local content; metadata changes alone must not imply a content conflict/download. Check capabilities, rather than promising every visible item is transferable. |
| Docs/Sheets/Slides are not ordinary downloadable blobs. `files.export` converts to a chosen supported format, with a **10 MB exported-content limit** and no partial export downloads. `files.download` also offers a long-running-operation route for Workspace content (and is required for Vids). [Export](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export), [Downloads](https://developers.google.com/workspace/drive/api/guides/manage-downloads), [LRO downloads](https://developers.google.com/workspace/drive/api/guides/long-running-operations) | Export is not lossless native-document two-way sync. Explicitly decide representation and local-edit/import semantics; do not silently replace a native Doc with an uploaded binary or assume round-trip fidelity. The 10 MB figure applies to `files.export`, not a demonstrated universal download ceiling. |
| A shortcut is its own file with `shortcutDetails.targetId`; its title is independent of its target's and it breaks if target access is lost/deleted. [Shortcuts](https://developers.google.com/workspace/drive/api/guides/shortcuts) | Decide whether to represent, follow, or hold shortcuts. Following must preserve shortcut/target identity, avoid duplicate traversal/cycles, and must not interpret deleting the shortcut as deleting its target. |
| `files.update(trashed=true)` is recoverable trash (automatically deleted after 30 days); `files.delete` permanently deletes without trash. Folder trash can make descendants `trashed` without `explicitlyTrashed`; permissions constrain destructive actions. [Trash/delete](https://developers.google.com/workspace/drive/api/guides/delete) | Define “delete both ways” explicitly: trash is a possible reversible remote policy, not equivalent to permanent delete. Do not multiply a parent trash into independent child destruction or empty the account trash as a sync operation. |
| A change's `removed=true` can mean deletion **or loss of access**; moving between corpora can also look removed. The unavailable item's metadata may be absent. [Change resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/changes), [Tombstones](https://developers.google.com/workspace/drive/api/guides/about-changes#tombstones) | Never turn every removal into local destruction. Preserve known baseline/tombstones and distinguish confirmed trash, permission loss, movement, and uncertain disappearance. Local edit versus remote disappearance must remain untouched until explicit conflict choice; the API does not resolve this policy. |

## Performance mechanisms—not a speed verdict

**[INFERENCE]** A native implementation could avoid repeat full-tree enumeration after bootstrap by retaining the Changes cursor and ID/parent index. It could request needed metadata in list/change responses instead of issuing one `get` per item, avoid content transfers when hashes are unchanged, and tune bounded transfer concurrency. None of this proves it faster than rclone: an existing engine may use the same mechanisms, and initial inventory, local scanning/hashing, many tiny-file round trips, conversion work, actual bytes, and server throttling still cost time.

Google documents partial `fields` responses, gzip, and metadata batching (at most 100 calls; each still counts separately); batches **cannot upload/download media or export files**. Resumable uploads reduce repeated transfer after interruption but add a session-start request; multipart can send small-file metadata and bytes together. These explain concrete latency/bandwidth tradeoffs, not benchmark results. Sources: [performance guidance](https://developers.google.com/workspace/drive/api/guides/performance), [upload types](https://developers.google.com/workspace/drive/api/guides/manage-uploads).

**Bottom line [INFERENCE]:** Native Drive provides inventory, durable incremental discovery, identity, transfer, and trash primitives—not a two-way reconciliation engine. Approval, persistent baselines, conflict holds and keep-local/keep-Drive/keep-both semantics, safe deletion classification, crash recovery, and a background worker remain application responsibilities. Scope/verification and filesystem mismatches are first-release constraints regardless of an unmeasured speed expectation.
